# Design Document: TIX-HUB Migration to TypeScript & PostgreSQL (Drizzle ORM)

**Author:** Antigravity  
**Date:** 2026-11-02  
**Status:** In Review  
**Target Architecture:** TypeScript, Node 22, PostgreSQL, Drizzle ORM, Redis, Express  
**Deployment Strategy:** Greenfield / Clean-slate deployment (no legacy MongoDB data migration or ETL required).  

---

## 1. Intent & Context

TIX-HUB is a real-time event ticketing and inventory management backend. Its core business requirement is handling high-concurrency ticket reservations with temporary holds (10-minute hold window) without allowing overselling or race conditions.

Currently, the service is written in JavaScript (CommonJS) using MongoDB via Mongoose. The MongoDB implementation suffers from multiple friction points:
1. Complex mocking and setup requirements for transactions (`mongoose.startSession()`).
2. Mongoose schema enum bugs (`'expired'` status rejected by schema in background cleanup).
3. Cache invalidation omissions (e.g. ticket cancellation does not bust event/availability caches).
4. Deprecated patterns in Mongoose hooks (mixing `async` and `next()` callbacks).
5. Misconfigured Redis client parameters for `node-redis` v4+.

This project migrates the entire codebase to **TypeScript** and ports the data layer from **MongoDB to PostgreSQL** using **Drizzle ORM**.

---

## 2. Goals, Non-Goals, and Anti-Goals

### Goals
- **Full TypeScript Migration:** Modern TypeScript (strict mode, ESM, `tsx` for local development, `tsup` for production compilation).
- **PostgreSQL & Drizzle ORM:** Replace MongoDB and Mongoose with PostgreSQL and Drizzle ORM.
- **Transactional Concurrency Safety:** Implement ticket holds and inventory changes using PostgreSQL transactions with row-level locking (`SELECT ... FOR UPDATE`) or atomic conditional decrements.
- **Bug Fixes:**
  - Update `ticket_status` enum to include `'pending'`, `'confirmed'`, `'cancelled'`, and `'expired'`.
  - Fix Redis client initialization (proper `socket: { host, port }` options and connection resilience).
  - Add missing Redis cache invalidations on booking cancellation (`cancelBooking`).
  - Align validation schemas (Zod) with Drizzle table definitions using `drizzle-zod`.
- **Environment & Build Modernization:** Clean `.env.example`, npm scripts for migrations, builds, and tests.
- **Test Suite Refresh:** Setup modern testing with Vitest (native TypeScript/ESM support) covering unit and integration testing.

### Non-Goals
- Altering the public HTTP API endpoints (`/api/v1/users`, `/api/v1/events`, `/api/v1/bookings`) or HTTP contract behavior. (IDs will move from 24-character hex Mongo ObjectIDs to standard UUIDv4).
- Adding new unrelated business features (payment gateways, multi-tier seat maps, etc.) during the migration.

### Anti-Goals
- Retaining Mongo-specific abstractions, packages (`mongoose`, `mockingoose`), or legacy CommonJS constructs.
- Relying on heavy runtime ORM binaries that obscure SQL lock primitives (e.g. Prisma's query engine).

## 3. Approaches Considered

### Approach 1: Drizzle ORM + `pg` (Selected)
- **Description:** TypeScript-first ORM mapping SQL tables directly to typed schemas, executed via `pg` connection pooling.
- **Why Chosen:** 
  - Direct support for PostgreSQL row locking (`.for('update')`) inside transactions.
  - No query engine binary overhead; near-zero bundle weight.
  - Seamless integration with Zod schemas (`drizzle-zod`).
  - Drizzle Kit provides clean SQL-based declarative migrations.

### Approach 2: Prisma ORM
- **Description:** Schema-first DSL (`schema.prisma`) generating TypeScript client code.
- **Why Rejected:** 
  - Native pessimistic row locking (`SELECT ... FOR UPDATE`) is not first-class in Prisma Client queries, requiring raw SQL `$queryRaw` workarounds for concurrency-safe ticketing.
  - Heavier deployment footprint due to query engine binaries.

### Approach 3: Kysely Query Builder
- **Description:** Lightweight, type-safe SQL query builder.
- **Why Rejected:** 
  - Lacks built-in declarative schema synchronization and migration ergonomics compared to Drizzle Kit, requiring more manual schema maintenance and validation plumbing.

## 5. Database Schema & Data Models

### 5.1 Tables

#### `users`
- `id`: `uuid` (Primary Key, default `gen_random_uuid()`)
- `name`: `varchar(100)` (NOT NULL)
- `email`: `varchar(255)` (UNIQUE, NOT NULL)
- `password`: `varchar(255)` (NOT NULL, bcrypt hash)
- `role`: `user_role` enum (`'user'`, `'admin'`), default `'user'`
- `created_at`: `timestamp with time zone` (default `now()`)
- `updated_at`: `timestamp with time zone` (default `now()`)

#### `events`
- `id`: `uuid` (Primary Key, default `gen_random_uuid()`)
- `name`: `varchar(255)` (NOT NULL)
- `description`: `text` (NOT NULL)
- `date`: `timestamp with time zone` (NOT NULL)
- `location`: `varchar(255)` (NOT NULL)
- `total_tickets`: `integer` (NOT NULL, check `total_tickets >= 1`)
- `available_tickets`: `integer` (NOT NULL, check `available_tickets >= 0`)
- `price`: `numeric(10, 2)` (NOT NULL, check `price >= 0`)
- `created_by`: `uuid` (Foreign Key $\to$ `users.id`, NOT NULL)
- `created_at`: `timestamp with time zone` (default `now()`)
- `updated_at`: `timestamp with time zone` (default `now()`)

#### `tickets`
- `id`: `uuid` (Primary Key, default `gen_random_uuid()`)
- `event_id`: `uuid` (Foreign Key $\to$ `events.id`, NOT NULL)
- `user_id`: `uuid` (Foreign Key $\to$ `users.id`, NOT NULL)
- `quantity`: `integer` (NOT NULL, check `quantity >= 1`)
- `total_price`: `numeric(10, 2)` (NOT NULL)
- `status`: `ticket_status` enum (`'pending'`, `'confirmed'`, `'cancelled'`, `'expired'`), default `'pending'`
- `hold_expiry`: `timestamp with time zone` (NULLABLE)
- `created_at`: `timestamp with time zone` (default `now()`)
- `updated_at`: `timestamp with time zone` (default `now()`)

*Indexes:*
- `tickets (hold_expiry)` (for fast expired hold scans)
- `tickets (event_id, user_id)`
- `events (date)`

## 6. Concurrency & Transaction Semantics

### 6.1 Creating a Booking (Holding Tickets)
```typescript
await db.transaction(async (tx) => {
  // 1. Lock the event row to prevent concurrent overselling
  const [event] = await tx
    .select()
    .from(events)
    .where(eq(events.id, eventId))
    .for('update');

  if (!event) throw new NotFoundError('Event not found');
  if (event.availableTickets < quantity) {
    throw new ConflictError(`Only ${event.availableTickets} tickets available`);
  }

  // 2. Decrement available inventory
  await tx
    .update(events)
    .set({
      availableTickets: event.availableTickets - quantity,
      updatedAt: new Date()
    })
    .where(eq(events.id, eventId));

  // 3. Create ticket record with 10-minute hold
  const holdExpiry = new Date(Date.now() + 10 * 60 * 1000);
  const [ticket] = await tx
    .insert(tickets)
    .values({
      eventId,
      userId,
      quantity,
      totalPrice: (Number(event.price) * quantity).toFixed(2),
      status: 'pending',
      holdExpiry,
    })
    .returning();

  return ticket;
});
```

### 6.2 Confirming a Booking
- Validate booking ID, status (`'pending'`), hold expiry (`holdExpiry > now()`), and user ownership.
- Update `tickets.status = 'confirmed'`, set `hold_expiry = null`.
- Invalidate availability cache in Redis.

### 6.3 Cancelling a Booking
- Transactionally lock ticket and associated event:
  - Return `quantity` back to `events.availableTickets`.
  - Update `tickets.status = 'cancelled'`.
- Invalidate Redis caches: `event:${eventId}`, `availability:${eventId}`, `events:*`.

### 6.4 Releasing Expired Holds (Background Job)
- Scan for `tickets` where `status = 'pending' AND hold_expiry < now()`.
- Within a transaction for each batch:
  - Increment `events.availableTickets += ticket.quantity`.
  - Set `tickets.status = 'expired'`.
  - Invalidate corresponding Redis caches.

## 7. Redis Caching & Resilience

- **Connection Config:** Use `socket: { host: env.REDIS_HOST, port: env.REDIS_PORT }`.
- **Fault-Tolerance:** App continues to serve requests cleanly if Redis is unavailable or disconnected. Cache reads return `null` (cache miss fallback) and cache writes gracefully catch and log errors.
- **Cache Invalidation:**
  - `invalidateEvent(id)`: deletes `event:${id}`, `availability:${id}`, and patterns `events:*`.
  - `invalidateUser(id)`: deletes `user:${id}`, `user:profile:${id}`, etc.
  - `invalidateBooking(eventId)`: deletes `availability:${eventId}`, `event:${eventId}`, `events:*`.

## 8. What's Left to the Builder
- **API Compatibility:** Primary keys in the database are standard `id` (UUIDv4). In API JSON responses, the serializer returns `id` and aliases `_id: id` to maintain backward compatibility with existing Postman tests and client scripts.
- **Background Hold Cleanup Execution:** Implemented in-process via `src/services/holdCleanupService.ts` running on a configurable interval (default 5 minutes). Uses PostgreSQL `SELECT ... FOR UPDATE SKIP LOCKED` inside transactions, allowing safe concurrent multi-instance operation without race conditions or external queue dependencies (e.g. BullMQ).
- **Selection between pure SQL migrations (`drizzle-kit generate / migrate`) vs auto-push for local test harnesses.**
- **Granular error mapping for PostgreSQL unique constraint violations (code `23505`) and foreign key violations (code `23503`) to custom `ConflictError` / `ValidationError`.**
- **Exact test runner tooling configuration (Vitest vs Jest-ts).**
